01 / STARTING POINT

A realistic jump is not necessarily a good game jump.

I started Signal Below by writing a simple gravity-and-collision loop. The more I played it, the more I noticed that the important questions were not only “Is the equation correct?” but also “Can the player predict it?” and “Does a mistake feel deserved?”

04 / DESIGN DECISIONS

Where the model bends

These rules are intentionally unlike a basic projectile model. Each one solves a specific control problem.

PROBLEM: LATE INPUT

Coyote time

The player may press jump just after the collision box leaves a ledge. I keep the last grounded state for seven frames before rejecting the input.

canJump = grounded ∨ t_since_edge < τ
PROBLEM: DIAGONAL SPEED

Vector normalization

The vector (1, 1) has magnitude √2. Normalizing it keeps diagonal and horizontal dashes at the same speed.

d̂ = d / √(dₓ² + dᵧ²)
PROBLEM: SOLID SURFACES

Collision geometry

I test axis-aligned rectangles, move on one axis at a time, and push overlaps back to the nearest surface.

Aₓ < Bₓ + Bw ∧ …
PROBLEM: ONE JUMP, TWO HEIGHTS

Variable jump height

When jump is released during ascent, extra gravity shortens the arc. Holding the button produces the full jump.

g′ = g + gcut

05 / CURRENT NOTES

What is not solved yet

01

The time step is not fully fixed

The current build scales movement by elapsed frame time but still counts a few actions in rendered frames. High-refresh-rate testing may reveal inconsistent timing.

02

Fast objects can cross thin walls

Collision is checked after movement. At a high enough speed, a player could move from one side of an obstacle to the other without overlapping it.

03

“Feels better” needs evidence

The present values came from playtesting and adjustment. I want to compare them systematically and record completion rate as well as player comments.

06 / WORKING METHOD

Question.
Test.
Change.

  1. 01

    Name one problem

    Start with a specific observation, such as overshooting a platform or missing a jump at its edge.

  2. 02

    Change one rule

    Keep the parameter and update rule visible so the same case can be repeated.

  3. 03

    Compare the result

    Check the predicted trajectory, the simulated trajectory, and what happens during play.

  4. 04

    Write down what failed

    A failed idea is useful if it narrows the next question. The repository keeps that history.
